# M1-S1 · Build-loop prerequisites

**Milestone:** `M1-acceptance-gate`

## Outcome

A dispatched round is bound to a task, and every round ends with a record the host computed itself.

When a builder reports done, the log carries a task identity nobody could have forged, and a frozen
hash of what was actually produced.

## Scope

**You may change:** `src/progressdesk/events.py` · `src/progressdesk/loop.py` ·
`src/progressdesk/runtime.py` · `src/progressdesk/desk.py`

**You may not change:** anything under `src/progressdesk/acceptance/` · `milestones.py` ·
`store.py` · `report.py` · any role brief.

**Already correct in this repo — read it, use it, do not rewrite it:**

- Reports are already per-round. `runtime.drain_reports()` and `runtime._round_dirs()` exist, and a
  report is attributed to the round directory it was found in — never by what its body claims. **You
  do not add a run id to anything.**
- `_digests()` already turns bytes into `{name: "sha256:..."}` against the content-addressed
  store, and `DispatchOutcome` already carries `.files`. You are hashing a map that exists. You are
  not building collection or storage.
- `DispatchOutcome.has_candidate` already means "this round produced an artifact." Use it; do not
  rename it.

**Your decision:** the shape of the hash helper · where the close is emitted in the dispatch flow ·
helper names in the two files you edit.

## Interfaces

You are building the substrate every later slice reads. Four events, three readers.

| event | payload you must provide | who reads it |
|---|---|---|
| `task.declared` | `taskId`, `milestoneId`, `spec` | populates a milestone's `required_task_ids` |
| `round.dispatched` | `taskId`, `milestoneId` | the delivery fold — this is the run→task binding |
| `round.closed` | `outcome`, `candidateHash`, `files`, `taskId`, `milestoneId` | the delivery fold, and the fixture assembler |
| `builder.reported` | `taskId`, added to the existing payload | the delivery fold |

**`round.closed.files` is the most load-bearing field you produce.** It is a `path → digest` map,
and the fixture assembler pulls each artifact out of the content-addressed store through it. Without
it, nothing can be assembled and nothing can be judged.

**`outcome` takes these values and no others:** `success` · `failure` · `killed` · `timed_out` ·
`cancelled`. Readers branch on exactly these.

**The task id is stamped by the host, from the dispatch record — never from the report body.** A
report naming a different task than the one it was dispatched against is an anomaly and counts as
nothing. This applies to both identities: the run comes from the round directory, the task from the
dispatch.

**`candidateHash` is computed by the control host from broker evidence for the candidate artifacts
at close time — never reported by the builder.** `killed` and `timed_out` carry
`candidateHash: null`.

**Do not add fields that nothing above reads.** If you believe you need one, you are outside this
slice.

## Acceptance

Nine checks. Each one exists and fails before you start.

1. `task_declared_event_exists` — the event is registered and a task can be declared
2. `dispatch_carries_task_and_milestone` — `round.dispatched` carries both
3. `round_closed_outcome_and_host_candidate_hash` — both present, hash host-computed
4. `killed_close_carries_null_hash` — and is never treated as delivered
5. `builder_filed_report_reaches_the_log_with_task_id` — filed through the report folder, arrives
   carrying the dispatched `taskId`
6. `report_task_id_stamped_from_dispatch_not_worker` — change the file body to claim a different
   task; it is still attributed to the dispatch
7. `report_task_contradiction_rejected` — a body naming a foreign task counts as nothing
8. `report_run_id_comes_from_the_round_directory` — no run id appears in the request
9. `report_asserting_a_fake_run_id_is_still_attributed_to_its_directory` — a fabricated run id does
   not redirect it

**Done when** all nine pass, and a real dispatched round in this repo leaves `task.declared`,
`round.dispatched`, and a `round.closed` in the log — with a `candidateHash` that changes when the
delivered bytes change.

**You are not done when the code compiles.** Check 6 is the one that will lie to you: the code works
whether or not the task id is stamped from the dispatch, and the check is what makes the difference
visible.
